# Feature map — where each LangChain / LangGraph capability is used

Every row points at code that actually runs in the pipeline (or in one of the four `examples/` scripts).
Nothing here is a snippet written to fill a table: if a feature is listed, the file named uses it, and
you can read it in context. Paths are relative to the repo root.

Installed versions: `langchain@1.x`, `@langchain/core@1.x`, `@langchain/langgraph@1.x`,
`@langchain/anthropic@1.x`, `@langchain/textsplitters@1.x`, `zod@4`.

---

## LangChain

| Feature | Where (file:symbol) | What to look at |
| --- | --- | --- |
| Chat model abstraction — custom `BaseChatModel` | `src/llm/fake-model.ts:ScriptedChatModel` | A rule-based model that is still a real `BaseChatModel`: `_llmType`, `_generate`, `_streamResponseChunks`, `_combineLLMOutput`, `lc_namespace`. It returns `AIMessageChunk`s (not `AIMessage`) because core's default structured-output parser requires chunks. This is what lets the whole demo run offline through genuine LangChain code paths. |
| Real provider — `ChatAnthropic` | `src/llm/factory.ts:createModels` | `new ChatAnthropic({ model, apiKey, maxRetries: 0, cache })`. `maxRetries: 0` is deliberate: `resilient()` owns retrying so it is visible in traces and in the run report, instead of hidden inside the SDK. `maxTokens` is deliberately left unset: Opus 5 runs adaptive thinking by default, and a cap would spend the budget thinking and truncate the answer before the tool call. |
| `ChatPromptTemplate` | `src/chains/extract.ts:buildExtractChain` (also `categorize.ts`, `summarize.ts`) | `ChatPromptTemplate.fromMessages([["system", …], ["human", "{payload}"]])`. Note the discipline: the invoice text is passed as a template **variable**, never as template text, so braces inside an invoice can't be parsed as f-string placeholders. |
| `FewShotChatMessagePromptTemplate` | `src/chains/categorize.ts:fewShotExamples` | Five vendor→category examples built from an `examplePrompt` of `["human", "{input}"] / ["ai", "{output}"]`, spliced into the middle of the message list between the system prompt and the real payload. |
| LCEL `RunnableSequence` | `src/chains/summarize.ts:buildSummaryChain` (also `extract.ts`, `categorize.ts`) | `RunnableSequence.from<In, Out>([lambda, prompt, model, parser])` — the four-stage shape every chain in the project follows. |
| LCEL `.pipe()` | `src/llm/factory.ts:resilient`; `examples/lcel-basics.ts` (step 1) | `build(models.primary).pipe(tagged(models.primaryTag))` composes the provider tag onto any chain; the example shows the canonical `prompt.pipe(model).pipe(new StringOutputParser())`. |
| `RunnableLambda` | `src/chains/categorize.ts:buildCategorizeChain`; `src/llm/factory.ts:resilient` | Used as adapters at both ends of a chain: rendering the prompt payload on the way in, re-parsing and normalising (`glAccount` is overwritten from the category map) on the way out. |
| `RunnableParallel` | `examples/lcel-basics.ts` (step 2) | `RunnableParallel.from({ category, digest })` runs the categorisation and summarisation chains over one shared input at the same time, each behind its own `RunnableLambda` adapter. |
| `.batch()` with `maxConcurrency` | `examples/lcel-basics.ts` (step 3) | `categorize.batch(inputs, { maxConcurrency: 2 })` — three inputs, at most two model calls in flight. |
| `withStructuredOutput` + zod | `src/chains/extract.ts`, `src/chains/categorize.ts` | `model.withStructuredOutput(ExtractedInvoiceSchema, { name: TOOL_NAMES.extract })`. Important caveat the code handles: core's default implementation returns the tool call's `args` **without validating them**, so both chains end with a `RunnableLambda` that calls `Schema.parse(raw)`. |
| `StringOutputParser` | `src/chains/summarize.ts:buildSummaryChain`; `examples/lcel-basics.ts` | The parser that turns model chunks into plain text and, crucially, streams — the summary node's tokens pass through it one at a time. |
| `tool()` + zod schema | `src/tools/recompute-totals.ts:createRecomputeTotalsTool`, `lookup-vendor.ts`, `find-duplicates.ts`, `search-policy.ts` | `tool(fn, { name, description, schema })` over zod 4 objects, with `.describe()` on every field. The descriptions are written as instructions to the model ("Call this whenever you need to confirm or dispute the arithmetic"), and `find_duplicates` interpolates the live policy window into its own description and returns three separate lists (`exact`, `sameNumberOtherVendor`, `similar`) so the agent cannot confuse a numbering collision with a second payment. |
| `bindTools` | `src/llm/fake-model.ts:ScriptedChatModel.bindTools` | Follows core's own convention: construct a new instance carrying the merged tools (via `this.constructor`, so subclasses survive) and `return next.withConfig({ tools })`. `normaliseTools` accepts OpenAI function dicts, Anthropic tool dicts and `StructuredTool`-likes. |
| `withRetry` | `src/llm/factory.ts:resilient` | `.withRetry({ stopAfterAttempt: models.maxRetries, onFailedAttempt })`, where `onFailedAttempt` **rethrows** anything `isRetryableError` rejects — that's how p-retry is told to stop immediately on a genuine bug instead of retrying it three times. |
| `withFallbacks` | `src/llm/factory.ts:resilient` | The primary chain is wrapped in a notifying lambda, then `.withFallbacks([build(models.fallback).pipe(tagged("fake"))])`. The `Tagged<T>` wrapper is what carries "which provider actually answered" into `ProcessedInvoice.provider`. |
| `InMemoryCache` | `src/llm/factory.ts:createModels` | Both providers are constructed with `cache: new InMemoryCache()`, so two byte-identical prompts cost one model call. Tool calls survive a cache hit; token accounting does not. |
| `BaseCallbackHandler` | `src/observability/usage-tracker.ts:UsageTracker` | A real callback handler overriding `handleChatModelStart` / `handleLLMStart` / `handleLLMEnd` / `handleLLMError` / `handleToolStart` / `handleToolEnd` / `handleToolError`. Reads tokens from either `llmOutput.tokenUsage` or the message's `usage_metadata`, and renders the per-model calls/tokens/cost table in the run footer. |
| `.stream()` token streaming | `src/graph/batch.graph.ts:streamText`; `examples/streaming.ts` (step 1) | `for await (const piece of await buildSummaryChain(model).stream(input, config))`. The example prints all 50 chunks as they arrive. |
| `streamEvents({ version: "v2" })` | `examples/streaming.ts` (step 2) | Tallies every runnable lifecycle event in the chain — `on_prompt_start`, `on_chat_model_stream` ×50, `on_parser_stream` ×50, `on_chain_end` — i.e. the whole tree, not just the output. |
| Custom `BaseRetriever` (BM25 RAG) | `src/rag/policy-retriever.ts:PolicyRetriever` | Subclasses `BaseRetriever<PolicyChunkMetadata>` with `lc_namespace` and `_getRelevantDocuments`, implementing Okapi BM25 (k1 1.5, b 0.75) with a small plural stemmer. No embedding provider needed, so RAG works offline. |
| `Document` + `MarkdownTextSplitter` | `src/rag/policy-retriever.ts:PolicyRetriever.fromPolicy` | `new MarkdownTextSplitter({ chunkSize: 400, chunkOverlap: 0 }).splitText(renderPolicyDocument(policy))`, each chunk wrapped in a `Document` carrying `{ section, chunk, score }`. The handbook is *rendered from* the typed policy, so quoted prose can never drift from the enforced numbers. |
| `createAgent` + middleware + `toolStrategy` | `src/agents/investigator.ts:buildInvestigator` | `createAgent({ model, tools, systemPrompt, middleware: [toolCallLimitMiddleware({ threadLimit: 8, exitBehavior: "end" }), modelRetryMiddleware({ maxRetries, retryOn: isRetryableError, onFailure: "error" })], responseFormat: toolStrategy(InvestigationReportSchema) })`, read back as `result.structuredResponse`. The response tool is named from the schema's JSON-Schema `title` (`InvestigationSchema.meta({ title })`) — `toolStrategy` has no name option. Pass the **raw** model: `createAgent` binds tools itself and rejects a pre-bound one. |
| `withConfig({ runName, tags })` | `src/llm/factory.ts:resilient`; `examples/lcel-basics.ts` (step 4) | `resilient()` stamps a run name (`extract`, `categorize`) on every chain so traces group sensibly. The example prints the run name and which child runs the tags reached. Honest note: core's callback typings and its runtime call disagree on argument order — `handleChainStart` is really invoked as `(chain, inputs, runId, parentRunId, tags, metadata, runType, runName)`, so the run name arrives as the **8th** positional argument even though the `.d.ts` names that slot `parentRunId`. `examples/lcel-basics.ts` (step 4) reads it from that slot and prints `runName reached: invoice-digest`. |
| Messages + tool-call plumbing | `src/llm/fake-model.ts:_generate` / `toToolCalls`; `src/agents/investigator.ts` | `AIMessageChunk` with `tool_calls: [{ id, name, args, type: "tool_call" }]` and `usage_metadata`, `ChatGenerationChunk` + `runManager.handleLLMNewToken` for streaming, `HumanMessage` for the agent's input. This is the wire format every provider has to produce. |
| LangSmith tracing (env passthrough) | `.env.example`; `src/config.ts:loadConfig` | `loadConfig` calls `process.loadEnvFile(".env")`, so `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT` land in `process.env` and LangChain's built-in tracer picks them up with no extra code. The app deliberately does **not** parse them into its own config — nothing here reads them, tracing is entirely LangChain's own env-driven behaviour. |

## LangGraph

| Feature | Where (file:symbol) | What to look at |
| --- | --- | --- |
| `StateSchema` | `src/graph/state.ts:InvoiceState`, `BatchState`, `ProcessInvoiceInput` | Three zod-typed state schemas — the per-invoice state, the batch state, and a narrow input schema for the `Send` target. Defaults are declared per channel (`.default(null)`, `.default(() => [])`). |
| `ReducedValue` reducers | `src/graph/state.ts:concat`, `upsertResults` | `issues`, `timings` and `deliveries` use `concat`/merge because parallel branches all write to them; `results` uses `upsertResults`, which merges by `documentId` and re-sorts — that is what lets a later human decision **replace** a fanned-in row instead of appending a duplicate of it. |
| `StateGraph` (+ context schema) | `src/graph/invoice.graph.ts:buildInvoiceGraph`, `src/graph/batch.graph.ts:buildBatchGraph` | `new StateGraph(InvoiceState, PipelineContextSchema)` — the two-argument form that types `config.context` inside every node. Both graphs end in `.compile()`; the batch graph passes a checkpointer. |
| Conditional edges | `src/graph/invoice.graph.ts:routeAfterRisk`; `src/graph/batch.graph.ts:nextAfterReview` | `addConditionalEdges("assess_risk", routeAfterRisk, ["investigate", "auto_approve", "auto_reject"])`. Both routers are exported pure functions, which is why they can be unit-tested without running a graph. |
| `Send` map-reduce fan-out | `src/graph/batch.graph.ts:fanOutRouter` | Returns `state.documents.map(document => new Send("process_invoice", { document }))` — one parallel subgraph run per document — or the string `"collect"` for an empty batch, so the graph still terminates cleanly. |
| Node input schema for a `Send` target | `src/graph/batch.graph.ts:buildBatchGraph`; `src/graph/state.ts:ProcessInvoiceInput` | `.addNode("process_invoice", …, { input: ProcessInvoiceInput })` — the node receives the `Send` payload shape, not the whole batch state. |
| Subgraph invocation with a different schema | `src/graph/batch.graph.ts:processInvoiceNode` | `await invoiceGraph.invoke({ document }, config)` — a graph with an entirely different state schema, run inside a node. Passing the parent `config` is what carries the context, the stream writer and the callbacks down into the child. |
| Parallel branches | `src/graph/invoice.graph.ts:buildInvoiceGraph` | `extract → validate` and `extract → categorize` both fan into `assess_risk`. Two edges out of one node is all it takes; the `issues` reducer is what makes it safe. |
| Cycles (the human-review loop) | `src/graph/batch.graph.ts` — `addConditionalEdges("review_next", nextAfterReview, ["review_next", "summarize"])` | The node loops back to itself while `reviewQueue` is non-empty, popping one document per pass. Visible as `review_next -.-> review_next` in `npm run graph`. |
| `interrupt()` | `src/graph/batch.graph.ts:askReviewer` | `interrupt<ReviewRequest, unknown>(payload)` throws `GraphInterrupt` to park the run; the payload is everything a human needs (risk, issues, the investigator's brief, the matching policy excerpts, how many are left). This node is deliberately **not** wrapped in `traced()`, because a `finally` would print a bogus "node finished" on every pause. |
| Multiple interrupts in one node | `src/graph/batch.graph.ts:askReviewer` | LangGraph replays a node from the top on resume, so the loop's second `interrupt()` is matched with the next resume value. An invalid resume payload is re-asked with `payload.error` set to the zod failure — up to `MAX_REVIEW_ATTEMPTS` (3), after which the invoice is left `needs_review` with `ABANDONED_NOTE` rather than hanging the run. |
| `Command({ resume })` | `src/pipeline/run-batch.ts:drive`, `resumeBatch` | `input = new Command({ resume: await opts.reviewer(pending[0]) })` — the answer is fed back in as the next stream input, and the loop repeats until nothing is pending. |
| Reading pending interrupts | `src/pipeline/run-batch.ts:pendingReviews` | `(await graph.getState(config)).tasks.flatMap(t => t.interrupts ?? [])` — how a caller discovers what the graph is waiting for. `resumeBatch` uses it to refuse a thread with nothing pending. |
| `MemorySaver` / `SqliteSaver` + `thread_id` | `src/graph/checkpointer.ts:createCheckpointer`; `src/pipeline/run-batch.ts:prepareRun` | `--checkpointer memory` (default) or `sqlite`, which writes `out/checkpoints.sqlite` and makes an interrupt survive process exit — that is the whole basis of the `resume` command. `configurable: { thread_id: threadId }`, thread id = batch id. |
| `context` / contextSchema (runtime DI) | `src/pipeline/context.ts:PipelineContextSchema`, `createPipelineContext`; every node's `config.context!` | Models, tools, ledger, retriever, policy, sinks and logger are injected per run and are never checkpointed, so live objects are safe to carry. The schema must be a real `z.object` (a bare `z.custom` is not a `StateDefinitionInit` and silently degrades the graph's types), so live fields are `z.custom<T>()` passthroughs inside an object. |
| `config.writer` — custom stream events | `src/graph/instrument.ts:emitProgress`, `traced`, `timed` | `config.writer?.(event)` publishes typed `ProgressEvent`s (`node_start`, `node_end`, `decision`, `delivery`, `info`, `warn`) on the `custom` channel. `timed()` also folds each node's duration into the state's `timings` map. The one event a node cannot emit honestly is `review_request`: LangGraph replays the `review_next` node on every resume, so an emit inside it would re-announce reviews already answered — `src/pipeline/run-batch.ts:drive` pushes it into the same stream once per genuine pause instead. |
| `streamMode: ["updates", "custom", "messages"]` | `src/pipeline/run-batch.ts:STREAM_MODES`; `src/observability/progress.ts:createProgressPrinter` | Three channels streamed at once and demultiplexed into one live log: `updates` detects `__interrupt__`, `custom` renders the progress events, `messages` writes summary tokens straight to stdout (filtered to `metadata.langgraph_node === "summarize"`). |
| Node `retryPolicy` | `src/graph/invoice.graph.ts` (`extract` node); `examples/retry-fallback.ts:nodeLevel` | `{ maxAttempts: 3, retryOn: isRetryableError, logWarning: false }`. Honest note: on `extract` it is unreachable in practice — the chain already retries and the node catches everything — and the code says so in a comment. The example has a one-node graph where the policy genuinely fires (throws twice, succeeds on attempt 3). |
| `getStateHistory` | `src/pipeline/run-batch.ts:settle`; `examples/time-travel.ts` (step 2) | Counted for the run footer ("10 checkpoint(s) on thread …" — root namespace only, subgraph namespaces excluded), and walked newest-first in the example to show `metadata.step`, `metadata.source` and each snapshot's `next`. |
| `updateState` (time travel) | `examples/time-travel.ts` (step 3–4) | `graph.updateState(target.config, { results: [...], reviewQueue: [] }, "collect")` forks history at an old checkpoint, then `graph.invoke(null, forked)` replays `summarize` and `deliver` from that fork — `null` input meaning "carry on from here". |
| `getGraphAsync().drawMermaid()` | `src/cli/commands.ts:graphCommand` | `(await buildInvoiceGraph().getGraphAsync()).drawMermaid()` — the source of both diagrams in the README, so they cannot drift from the compiled graphs. |
| `maxConcurrency` throttling the fan-out | `src/pipeline/run-batch.ts:prepareRun` | `maxConcurrency: opts.config.concurrency` in the run config; LangGraph's task runner honours it, so `--concurrency` really does limit how many `Send` branches run at once. |
| `executionInfo.threadId` | `src/graph/batch.graph.ts:threadIdOf` | The typed way to read the current thread id **inside** a node. `LangGraphRunnableConfig<C>` types `configurable` as the context type, so `config.configurable?.thread_id` does not typecheck; `config.executionInfo?.threadId` does (and is `undefined` without a checkpointer). |
| `START` / `END` and graph termination | `src/graph/invoice.graph.ts`, `src/graph/batch.graph.ts` | Every terminal decision node runs to `END`; the batch graph's `deliver → END`. Combined with the bounded review loop and the empty-batch short circuit, there is no path that can spin forever. |
